DeepSeek Harness 开源那天，我写了一篇文章，里面有句话其实挺刺人的：它的 Trace 链路和我们做的 DataClaw「几乎一模一样」。

当时是兴奋，事后是警觉。

一个团队花了很长时间摸索出来的架构，被一家模型公司在一次开源里顺手做掉了。这件事值得认真对待：**如果我现在做的东西，大厂在一个版本里就能覆盖掉，那它就不是护城河，只是一段领先时间。**

所以这篇文章我想把问题摆到桌面上：数据智能体这件事，从第一性原理看到底在解决什么，我们有没有护城河，GTM 该怎么打，PMF 到了哪一步。

## 一、第一性原理：数据智能体到底在卖什么

先把包装剥掉。

数据智能体不是「用自然语言查数」，也不是「NL2SQL」。这些是实现手段，不是价值本身。

从第一性原理看，企业里一直存在一条固定链路：

```
业务问题 → 找到正确的数据 → 用正确的口径计算 → 得到可信结论 → 做决策
```

过去这条链路上站着人：业务提需求，分析师写 SQL，数据工程排任务，出报表，再来回对口径。这条链路的成本结构里，**最贵的不是计算，是人和沟通，以及等待**。

数据智能体真正在做的事，是把这条链路上的人力和时延压到接近零。

这就推出三个不能绕开的结论。

**第一，价值不在生成，在可信。** 生成一段 SQL 的边际成本已经接近零，任何模型都能做。但一个错误的数字，代价远远高于十个正确的数字带来的收益。业务只要被坑一次，之后就再也不看你的结果了。所以数据智能体的核心竞争力不是「答得出来」，而是「答得对，并且我知道它什么时候会答错」。

**第二，瓶颈不在模型，在上下文。** 模型不知道你们公司的「有效收听」怎么算、去年口径改过一次、某张表从三月起废弃、某个渠道的数据有两天延迟。这些东西不在互联网上，不在预训练数据里，只在企业内部的人脑、文档和历史工单里。模型越强，这部分的相对重要性反而越高，因为通用能力被拉平之后，差异只剩私有上下文。

**第三，终局形态不是问答，是交付。** 用户要的不是一次对话，而是一个结果：昨天的异动是什么原因、这个活动值不值得追投、这份日报直接发出去。对话只是入口，交付物才是产品。

如果这三条成立，那么后面所有关于护城河、GTM、PMF 的讨论都应该围绕它们展开。

## 二、四个视角的诚实体检

### 产品视角：形态正在收敛，锚点必须换

数据智能体的产品形态这两年经历过三代：

1. 一个聊天框，问一句答一句（ChatBI 1.0）
2. 多智能体分工，带规划、带反思（ChatBI 2.0）
3. Agent + Harness + 场景交付物：可执行、可回放、可审计、可被别的系统调用

第三代的关键变化是，**产品的度量单位从「对话轮次」变成了「任务完成率」**。

这件事对产品设计的要求完全不同。对话体验可以靠 Prompt 打磨，任务完成率必须靠工程：工具协议、权限边界、失败重试、中断恢复、执行轨迹。这恰恰是 Harness 层的事情。

一个容易犯的错误是把产品锚点放在「像人一样聊天」上。真实的锚点应该是：

- 用户提出一个任务，系统在多久内给出可用结论
- 这个结论有多大比例可以直接拿去用，不需要人工复核
- 出错的时候，用户能不能自己看出来它错了

第三条最容易被忽略，但它决定信任能不能建立。一个会明确说「这个指标口径有两个版本，我用的是 A」的系统，比一个总是自信给出数字的系统有价值得多。

### 技术视角：做一次「拔掉模型」的思想实验

判断技术护城河，有个很简单的办法：**把底座模型换成另一家，把开源 Harness 摆在旁边，看你还剩下什么。**

剩下的东西里，再问一句：这部分别人三到六个月能不能做出来？

按这个标准分三层。

**会被抹平的（没有护城河）：** 自然语言转 SQL 的基础能力、对话 UI、单点 Agent Loop、模型路由、通用工具调用、基础的 Trace 展示。这些要么是模型能力本身，要么是通用工程问题，模型厂和开源社区一定会覆盖。DeepSeek Harness 已经证明了这一点。

**有窗口期但可复制的（半年到一年的领先）：** Harness 的工程成熟度、插件化架构、权限与沙箱策略、上下文组装的工程技巧、评测流水线。这些确实需要踩坑积累，但坑是公开的，别人踩得会比你快。领先时间有价值，但不能当资产记账。

**可以复利的（真正的护城河）：**

- **私有语义层与口径知识。** 指标定义、血缘关系、业务黑话、口径变更历史、数据质量的已知坑。这是企业内部长期沉淀出来的，任何外部产品都拿不到。它越完整，模型的表现越好，而且这个优势不随模型换代而消失。
- **真实执行轨迹与失败归因数据。** 这是我一直强调的 Co-Design 飞轮：真实任务产生轨迹，轨迹经过评测和归因，同时反馈给模型侧和 Harness 侧。但要说实话，**光有日志不算数据资产**。如果没有标注过的评测集、没有失败分类体系、没有回归基线，那些日志只是磁盘占用。这条护城河是「可以有」，不是「自动有」。
- **与执行系统的耦合深度。** 能查数只是起点。能改调度、能补数、能提治理工单、能把结论写回业务系统，这些权限和链路是外部产品进不来的地方。

把这三层对齐一下，结论就比较清楚了：**我们现在的领先大部分在第二层，第三层才刚开始。这不是什么好消息，但知道比不知道好。**

### 商业价值视角：别用技术指标冒充价值指标

内部数据智能体最容易陷入的自我欺骗，是拿调用量、token 消耗、接入表数量当成果汇报。这些是成本指标，不是价值指标。

真正能对齐业务语言的价值只有四类：

1. **人力替代：** 原来需要分析师介入的取数和归因，现在有多少比例被自助完成。可以直接折算工时。
2. **时延压缩：** 一个业务问题从提出到拿到可信结论的时间，从天级到分钟级。快出来的那段时间，价值体现在决策质量上。
3. **覆盖面扩张：** 过去因为排期排不上而根本没人去分析的问题，现在被分析了。这部分是纯增量，也最难量化，但往往是最大的价值。
4. **治理反哺：** Agent 用不好的地方，精确暴露了数据资产的问题——口径混乱、表没有注释、血缘断裂。这让数据治理第一次有了明确的优先级依据。

第四条常常被低估。过去数据治理是一件「重要但没人急」的事，有了数据智能体之后，治理质量直接决定 Agent 的任务完成率，治理终于有了一个会天天喊疼的用户。

### 公司价值视角：被依赖度大于技术领先度

对内部平台团队来说，公司价值不由技术先进程度决定，由被依赖程度决定。

一个判断标准很残酷但很准确：**如果这个系统明天下线，谁会第一时间打电话过来？**

如果答案是「没人」，那它就是一个 demo。如果答案是「运营和财务的日报出不来」，那它已经进入业务流程，价值就是结构性的。

由此可以得到几个危险信号：

- 系统的主要流量来自于新鲜感和内部推广，而不是重复的日常工作
- 用户画像里只有技术团队和数据团队，没有真正的业务决策者
- 大会上讲得很好，业务方的工单量一点没降

以及几个健康信号：

- 有人在没人催的情况下，把它加进了自己的日常流程
- 业务方开始主动提功能需求，而且愿意为此贡献口径梳理的工作量
- 其他团队要求接入 API，把它当基础设施而不是产品

## 三、所以到底有没有护城河

我的结论是：**有护城河的可能性，但现在还不算真的有。**

拆开说。

**已经有的：**

- 场景纵深。在自己公司的数据环境里踩过的坑、建立的口径映射、积累的业务语义，这些是实打实的资产，外部产品短期内做不到。
- 组织位置。已经在真实业务流程里的那部分，有切换成本。
- 工程判断力。做过完整 Harness 的团队，知道哪些路走不通，这能省下大量试错。

**还不算有的：**

- 数据飞轮还没转起来。轨迹有了，但轨迹到评测集、评测集到改进闭环这段，如果还依赖人工看 case，那就不是飞轮，是手摇。
- 语义层还没有变成资产。如果口径知识主要还在少数人脑子里和散落的文档里，而不是结构化、可被 Agent 消费、可被增量维护的一层，那它随人员流动而蒸发。
- 交付物还不够刚性。能回答问题和能承担一份每天必须发出的报告，是两种完全不同的责任级别。

**根本不是护城河但容易误认为是的：**

- 团队会做 Agent。三年内这会变成基础技能。
- 架构做得比开源早。DeepSeek Harness 已经说明了这件事的保质期。
- 演讲和影响力。它对招聘和认知有用，对产品壁垒没用。

顺着这个思路，护城河的判定只有一个问题：**当模型能力再翻一倍、开源 Harness 免费且成熟之后，我手里还剩什么别人拿不走的东西？**

剩下的答案只能是：企业私有的语义与口径资产，被标注和结构化的失败数据，以及深度嵌入业务流程的执行权限。**其余一切都在贬值。**

这也意味着投入优先级应该调整：与其继续在框架层追新，不如把语义层和评测体系做成真正的资产。

## 四、GTM：内部平台的 GTM 是采纳曲线

内部产品也有 GTM，只是货币不是钱，是注意力和信任。

### 最常见的死法

全员发布 → 大家好奇来试 → 有人问了一个开放问题 → 答错或者答得似是而非 → 一传十 → 「这东西不准」→ 之后再准也没人回来了。

信任是非对称的，建立慢，摧毁快。所以内部 GTM 的第一原则不是铺开，是**先赢，再扩**。

### 我认为正确的顺序

**第一步，选场景不选用户。** 挑那种高频、口径确定、答案可验证的场景做到极致。日常核心指标查询、日报生成、固定维度的异动归因，这些确定性高。开放式探索、因果推断、战略建议，现阶段不要碰，它们既做不好又最容易毁信任。

**第二步，抓关键节点用户。** 不要全员推广。找那几个每周被取数需求压垮的分析师，和那几个真正要看数做决定的业务负责人。分析师是产品的共建者，也是最严厉的验收者；业务负责人决定这件事在组织里有没有分量。

**第三步，嵌入已有入口。** 不要指望用户记住一个新网址。入口应该在他们已经待着的地方：IM、现有 BI、工单系统、日报推送。少一次跳转，留存差别很大。

**第四步，把工单流量当成度量。** 内部数据智能体最硬的 GTM 指标，是取数工单量的下降曲线。这个数字骗不了人，也最容易讲给管理层听。

**第五步，明确「错了怎么办」。** 每个结论都要能追溯到表、字段、口径和执行过程。要有一键转人工的通道。坦白说不会的问题，比硬答一个更能积累信任。

### 一套可以直接用的 GTM 漏斗

- 触达：目标人群里有多少人知道并试过
- 首次成功：首次使用就拿到可用结果的比例
- 次周留存：这是分水岭，尝鲜和采纳在这里分开
- 使用深度：人均每周发起任务数
- 采纳率：结论直接被使用、不需要人工复核的比例
- 替代率：相关取数工单的同比下降幅度

这几个数拉出来，团队对自己处于什么阶段就不会有幻觉了。

### 关于对外

如果考虑对外（开源或商业化），要清楚一件事：**通用数据智能体的对外 GTM，正面对手是模型公司和云厂商，这一仗打不赢。**

可行的方式是错位：把 Harness 和语义层规范开源出去，换生态、换标准话语权、换人才；把评测体系、治理闭环和行业语义模板留在手里。但在内部团队阶段，对外的主要收益是招聘和认知，别把它当成商业路径来算账。

## 五、PMF：不要问整体，要按场景问

PMF 最容易被误读成「有人用」。

真实的判定标准只有一个：**如果现在把它关掉，有多少人会抗议。**

按这个标准，数据智能体的 PMF 必须拆到场景粒度，因为不同场景的成熟度差距极大：

| 场景 | 确定性 | PMF 现实情况 |
| --- | --- | --- |
| 核心指标查询、口径明确的问数 | 高 | 最容易达到，也最该先做到 |
| 日报、周报等固定交付物 | 高 | 一旦跑顺，粘性极强，是最好的护城河入口 |
| 有限维度的异动归因 | 中 | 能做，但需要强语义层和明确的归因框架 |
| 多轮深度分析、因果推断 | 低 | 现阶段基本靠人，Agent 只能做辅助 |
| 开放式战略探索 | 极低 | 没有 PMF，做了也是演示用 |

所以「我们有没有 PMF」这个问题本身就问错了。正确的问法是：**在哪几个场景上已经有 PMF，能不能说出证据。**

### 有 PMF 的证据长什么样

- 留存曲线走平，而不是持续下滑
- 有用户自发把它推荐给同事，推广不靠行政力量
- 用户开始抱怨功能不够，而不是抱怨结果不准
- 出故障的时候有人立刻来问什么时候恢复
- 业务方愿意为了让它更准，自己投入时间梳理口径

### 没有 PMF 的信号

- 活跃度和内部推广活动高度相关
- 用户平均使用两三次就消失
- 每个结论都要人工复核一遍才敢用
- 大家夸架构好，但没人依赖它工作

## 六、如果只做三件事

写到这里，结论其实收得很窄。

**第一件，把语义层从文档变成资产。** 指标定义、口径版本、血缘、已知数据坑，结构化、可被 Agent 消费、可增量维护、有明确的负责人。这是唯一随时间升值、且模型换代不影响的东西。

**第二件，把轨迹变成评测集，把评测集变成回归基线。** 没有稳定评测集的 Agent 团队，改进全靠感觉，每次迭代都可能在悄悄退化。飞轮的启动点不是日志，是标注。

**第三件，在一到两个高确定性场景上做到「关掉会有人抗议」。** 宽度可以以后再说，深度决定生死。一个被业务真正依赖的场景，价值大于十个演示得很漂亮的能力。

模型会越来越强，Harness 会越来越像，框架层的领先会不断被清零。能留下的只有两样：**别人拿不到的上下文，和别人替代不掉的位置。**

其余的，都是时间差。
